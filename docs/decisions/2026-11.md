### 2026-11-12 — The measured ground is reverted out of 019 and deferred to task 020, because hard-edged panels reintroduced the look the frosted-panel retirement removed

The ground ruled in earlier today was built, measured, reviewed and reverted inside the same task. The owner
saw the before/after and judged the change to the plain page too large. The work is not lost: the figures,
the sampler and the shape findings all carry into **task 020**, and `--surface-glass`, `--surface-blur` and
the `.surface-frosted` utility are held for it rather than deleted under 019's criterion 48.

**What was built and what it achieved.** A `--ground-scrim: rgb(0 0 0 / 0.36)` painted through an
`@utility ground-scrim` `::before` (no box, so no layout shift), reaching `0.5rem` past four hosts: the chip
row, the digits frame, the Start/Reset row and the bottom-button cluster. It cleared every surface on every
ground and lowered no plain-page figure: checked chip 2.45 to 5.05, unchecked 2.37 to 4.88, control edges and
focus ring 1.66 to 3.43, digits held at 4.68 against the gauge liquid rather than the image. The owner's
original 0.25 to 0.30 estimate was too weak; 0.28 measured 4.08 on the unchecked chip and 2.87 on the edges.

**Why it was reverted, which is the part 020 must not repeat.** All four grounds were hard-edged rounded
rectangles inset uniformly. That shape is what made them read as *panels*, which is what the frosted-panel
retirement was taken to remove, so the fix reintroduced the look it was supposed to work around. Three
specific faults, from the screenshot comparison:

1. The digits ground put a rounded rectangle behind an already-rounded gauge capsule, so a frame sat inside a
   frame. It read as a layout bug, not a surface.
2. The chip-row ground stopped just above the four cycle dots, orphaning them from the row they belong to.
3. Only the Start/Reset and bottom-button grounds read correctly, and those two hug their buttons closely.

So the technique is sound and the alpha is near the floor (edges and ring clear 3.0 by 0.43), but the
**geometry** is the open problem: a ground shaped to its content, feathered rather than cut off, with the
dots inside the chip host. That is 020's brief, not a second attempt at the same rectangle.

**What 019 keeps.** The task-title focus ring, which was missing entirely (`outline-none!` with no
replacement, pre-existing from task 016), is an accessibility fix independent of the ground and stays. The
overlay `opacity-50` was never touched in either direction. Criteria 37 to 40, 42 and 43 move to 020; 41 and
44 stay satisfied in 019.

### 2026-11-12 — Task 019 approved: dark is the only theme, the dark palette becomes the base, and a scrim is a fix for a measured miss rather than a default

Dark is the only theme. The LIGHT / DARK / SYSTEM selector, the light palette, the `theme` store field and
the theme-resolving boot logic all go. The reason is the owner's: custom uploaded backgrounds look poor in
light mode, dark looks good, and one palette is cheaper to maintain than two. Task 018 shipped the derived
`hasCustomBackground ? "dark" : preference` rule the same day and is **superseded** by this — its
theme-lock machinery is deleted, its background work (`components/BackgroundProvider.tsx`, the
`pending | present | absent` read) stays.

**Three things a later task would otherwise re-ask.**

1. **D1 — the dark palette becomes the base (option b), not a statically-applied `.dark` class (option a).**
   Counted before choosing: `:root` defines 41 custom properties, `.dark` overrides 32, and the 9 it leaves
   alone are `--radius` plus eight `--sidebar-*` tokens that **no file in `app/`, `components/`, `widgets/`
   or `hooks/` reads** — only `app/globals.css` itself and two test files. Live `dark:` Tailwind variants in
   application code: exactly **one**, `components/ui/checkbox.tsx:16`. The three hits in
   `components/ui/button.tsx` are comments recording an earlier removal, and `ThemeControl.tsx:14` is the
   object key `dark: "Dark"`, not a variant. So flattening is: move 32 values into `:root`, delete the 9
   light-only leftovers, delete `.dark` and `@custom-variant dark`, de-prefix one utility. Option (a) would
   keep two blocks and a class that nothing may ever remove — a second thing to keep true forever, for a
   smaller diff today. The condition on (b) was "only if clean and low-risk"; one live variant is as clean
   as it gets. Colours stay named CSS variables either way, so a second theme later means redefining
   variables, not editing components. The one real cost: each `.dark` value carries painted-pixel contrast
   provenance in comments (`app/globals.css:53-54`, `:205`, `:225`) that has to travel with the value it
   documents — losing that is how a later task re-measures something already measured.

2. **The stale preference is removed as a field, never as a key.** The owner's wording was "remove the stale
   key on load". Taken literally that destroys unrelated settings: `theme` lives at `state.theme` **inside**
   the single zustand-persist key `pomotato-preferences`, which also holds `background`,
   `taskPanelVisible`, the gauge style and the session lengths. So the field is dropped and the siblings are
   asserted unchanged. A stored `light`, `dark`, `system`, unknown string, `null` or non-string must all
   boot without error and without a visual difference from no stored preferences at all; none of them is
   mapped into any other preference or default.

3. **A scrim is a fix for a measured miss, not a default.** The dark-robustness requirement asks for a scrim
   or frosted panel behind the timer and main controls. A localized frosted panel was retired by ruling
   earlier the same day, and the requirement is really the **ratio** (4.5:1 text, 3:1 UI), not the
   technique — so the bound gets measured first (a white image and a high-frequency busy image bound the
   range) and a ground is added only for a surface whose painted-pixel sample misses. Where a surface
   already clears, the measurement proving it is recorded and nothing is added. Any ground that is added
   must change no pixel outside the timer's and controls' own bounding boxes on the plain page, must cost
   no contrast there, and if it shifts the plain-page look noticeably the before/after goes to the owner
   before the task closes. Reversing the frosted-panel retirement outright remains the owner's call, not
   frontend's. The background overlay stays at `opacity-50`, byte-for-byte.

Also settled: no Dexie involvement (`grep -rin theme lib/db/` is empty), so `backend` does not run and
`frontend` owns the whole task. `e2e/helpers/dark.ts` is imported by nine specs and gets one decision for
all nine — neutered or deleted — not half on each path. Two `docs/PLAN.md` items lose their subject with
the selector (the wordmark halo over the theme chip's focus ring, `--dialog-edge`'s light sub-floor) and
are marked obsolete when 019 closes rather than fixed in it.

### 2026-11-12 — Task 018 approved and shipped: a custom background locks the theme to dark and hides the selector, and the background read moves to one layout-level owner

Owner requirements the same day, approved the same day, shipped the same day. Light mode was unreadable over
an uploaded image and dark mode was judged acceptable, so the effective theme becomes **derived**:
`hasCustomBackground ? "dark" : userPreference`. The stored preference is never overwritten, so removing the
background restores exactly what was there, `system` included. The LIGHT / DARK / SYSTEM selector hides while
a background is on. No schema change: `state.background` was already in the zustand-persist envelope the
pre-hydration boot script parses.

**Three things a later task would otherwise re-ask.**

1. **`hasCustomBackground` means "settled present", and `pending` counts as locked.** `useBackgroundImage`
   returned `string | null` and collapsed "still loading" into the same `null` as "dangling id" and "will not
   decode". Criteria 23, 26 and 28 need those apart, so the read moved to a single owner,
   `components/BackgroundProvider.tsx`, mounted in `app/layout.tsx` beside `ThemeSync` and exposing
   `pending | present | absent`. Only a settled
   `absent` unlocks. The rejected alternative — locking on the stored id alone, which is synchronous and
   flash-free — would leave `/settings` locked to dark **with the selector hidden and nothing on that route
   able to learn the blob is dead**. The accepted price: `/settings` and `/stats` pay one Dexie read and one
   decode they did not pay before.

2. **First paint is CSS's job, the settled state is React's.** The boot script sets `data-theme-lock="locked"`
   from the same computed value that forces the dark class, so the two cannot drift, and CSS hides the
   selector on that attribute. After hydration `ThemeControl` returns `null`, so the fieldset is genuinely
   absent rather than hidden. This follows the `data-task-panel` precedent from task 015. Without the
   attribute the selector flashed in and out on every reload with a background — the theme never did, but the
   selector did, and no criterion would have caught it.

3. **Dark over a bright image does not clear the contrast floor, and 018 is not what broke it.** Measured in
   dark with the overlay at `opacity-50`: timer digits **3.02-3.62**, wordmark **1.73-1.87**, against a 4.5
   text floor. The one passing figure, 4.68, passes only because the *vessel* gauge puts its own fill under
   the digits; glyph gauge puts them on the image. Per reviewer, these ratios are a property of the overlay
   rather than of this task, and 018 raises contrast over an image because the state it replaces is light ink
   on the same ground. Routed to the owner under criterion 43; the overlay was **not** changed, and a change
   to it is not the default fix. Carried on PLAN.md as its own decision.

**Rejected: adopting AI Blueprint** (`https://ai-blueprint.dev/`), which the owner raised as a candidate.

path, which is what the brief/log split does.

**The honest target.** Under ~20k tokens *per agent run* is reachable and is now written into each agent

way to make a task cost 20k is to stop classifying it as major; see "Three sizes of work, not two".

### 2026-11-11 — The session-end chime fires on every route, and its guard is deliberately not the announcement's

Implemented first as an effect inside `components/PomotatoTimer.tsx`, which mounts only on `/`. A session
ending while the person sat on `/settings` or `/stats` made no sound and was advanced silently on their next
visit — including, absurdly, while they were adjusting the timer's own settings. The owner ruled it fixed.
`components/TimerClockProvider.tsx` now mounts in `app/layout.tsx` and owns the clock, `completeIfExpired`
and the chime; `PomotatoTimer` reads `useTimerNow()` for its display only, so the clock still runs once.

**The chime guard and the announcement guard are intentionally different, and must stay different.**
`chimedAdvanceRef` lives in the provider, which never unmounts, so a `/` → `/settings` → `/` round trip around
a completion cannot replay the sound. `announcedAdvanceRef` stays in `PomotatoTimer` and is seeded on mount
from the existing `lastAdvance`, so returning to `/` long after an advance that happened elsewhere does not
announce stale news to a screen reader. Both still key on `lastAdvance.endedAt`, and `onRehydrateStorage`
still clears `lastAdvance`, which is what makes "no chime on refresh" true.
**How to apply:** the asymmetry reads like an inconsistency and is not one. The chime is for an advance observed
anywhere; the live region is for one observed on `/`. There is a comment saying so next to the ref — do not
"align" them.

### 2026-11-11 — Three task 017 criteria ruled by the orchestrator: a legend is a section heading, a fixture seed is not a shipped duration, and a refused chime may be stopped

**Criterion 1's heading-level clause is satisfied by `fieldset`/`legend`.** Both new sections use a legend,
matching the existing "Timer gauge" section, so `/settings` has one `h1` and no `h2` at all. A `<legend>` is
the correct element for a group of form controls and supplies the group's accessible name; no level is skipped

**Criterion 9's single-source rule governs shipped source, so `lib/db/test-utils.ts:45` is exempt.** Its

third home for a hard-coded `5` and `15` and has been pointed at the constants.

**Criterion 38's "no stop before the scheduled end" is not absolute — `abandon()` may stop a refused chime.**
It runs only on `blocked` or `failed`, when the context never started, so nothing audible is truncated, and it
nulls `onended` first so teardown cannot double-fire. Leaving the oscillators scheduled on a dead context is
the actual defect, since that was the leak.
**How to apply:** keep that qualifier attached. The criterion protects a *playing* chime from being cut by the
mode transition; it says nothing about tearing down one that never sounded.

### 2026-11-11 — A JS timer bounds a blocked `AudioContext` resume, because a suspended context's clock cannot

Under Chrome's autoplay policy `context.resume()` neither resolves nor rejects until a gesture arrives. The
first implementation did `await lease.ready` with no bound, so `play()` never settled: the required
`console.warn` never fired (qa's criterion 53 failure), teardown never ran, and — the part the failure
report missed — `chimesInFlight` was incremented at `engine.ts:286` but only decremented in `release`, so it
stuck above zero permanently and the gates at `engine.ts:190` and `:269` could never suspend the context
again. **One blocked chime disabled suspension for the life of the page.**

The fix bounds the wait at 500 ms via `settleWithin` and classifies a pending resume as `blocked`. The timer
lives in `lib/settle-within.ts`, **outside** `lib/audio`, because putting it in `engine.ts` tripped two existing
timer-ban guards.
**Why this is not guard evasion, which was checked rather than assumed:** criterion 46's intent is that no JS
timer drives the sound and teardown runs on the audio clock. On the audible path the context is already
running, the timer is created and cleared in the same microtask and never fires, and teardown still comes from
`oscillator.onended`. On the blocked path the audio clock is frozen *by definition*, so it cannot measure the
wait. Reviewer checked the alternatives: a synchronous `state !== "running"` verdict misclassifies the engine's
own idle-suspend, where `resume()` does settle in tens of milliseconds, and `statechange` can tell you a context
started but never that it never will. A bounded wait is the only available answer.
**How to apply:** the defence is a module boundary, so the boundary is now guarded — `lib/settle-within.ts` is in
the criterion 46/74 scan with one exact-text exemption, so a second timer there, or widening `settleWithin` into
something that schedules sound, fails a gate. Do not remove that scan entry; without it the argument above is
unenforced.

### 2026-11-10 — The layout-shift metric measures the painted rect, so an arriving shadow shifts a box that never moved

Task 012 criterion 22 ("the image's arrival moves nothing") failed at 320 px on the shipped tree: the
no-image load totalled **0.19547067901234566** of layout shift and the image load **0.19666165123456789**,
a delta of **0.0011909722222222252**, against an assertion of equality to six decimals
(`e2e/focus-surface-behaviour.spec.ts:116`). The two `sameGeometry` assertions above it **passed**, so no
layout box moved.

**The orchestrator's diagnosis was wrong, and the way it was wrong is the point.** It reasoned from recency:
the glyph halo had just shipped, `-webkit-text-stroke` paints outside the letterforms, so the halo's arrival
must be growing the wordmark's painted rect. That is a coherent story and it is false. Making the stroke
width unconditional and flipping only its colour — the fix ruled on from that diagnosis — changed the figure
**not at all**: still 0.19666165123456789 against 0.19547067901234566.

**The actual shifted node is the task panel.** Dumping the shift sources for the 320 px load in both states
puts neither the wordmark nor the chips among them. The node is the task-list `section`'s `surface-solid`
div: rect `16,554 288x166` with no image, `13,552 294x168` with one. The 3 px left and 2 px top growth is
`box-shadow: 0 1px 2px 0 rgb(0 0 0 / 0.08)`, which **exists only while an image is active** — it is declared
inside `body:has([data-background="active"]) &` and nowhere else. Chromium counts a shadow's painted overflow
in the layout-shift rect, so the shadow's *appearance* is a shift of a box whose layout never changed.

**Fix: declare the property transparent in the no-image state rather than omitting it.** Both
`surface-solid` and `surface-frosted` now carry `box-shadow: 0 1px 2px 0 transparent` at rest, and the
active rule changes only the colour. The painted extent is then identical in both states and the arrival
adds zero. The same treatment is applied to `.glyph-halo`'s stroke — not because it was the cause, but
because it is the same shape of hazard and the uniform rule is cheaper to keep than a per-property
exception. Criterion 22 passes at 320 and 1280, verified by the orchestrator on its own build.

**The reusable rule, two parts.**
1. **A property that appears on arrival must be declared at rest with a transparent value, not left
   undeclared.** This applies to every `box-shadow`, `outline`, `text-stroke` and `filter` behind the
   `body:has([data-background="active"])` gate — the whole surface system is built on properties that
   switch on with the image, so any of them can do this. CLS reads the painted rect; `sameGeometry` reads
   the layout box; **a criterion that asserts both needs both, and passing the second tells you nothing
   about the first.**
2. **Find the shifted node before theorising about it.** `PerformanceObserver`'s layout-shift entries carry
   `sources`, each with the node and its previous and current rects. One dump settled in minutes what a
   plausible story about the most recent commit got wrong. Same family as the 2026-11-06 `liveQuery` entry,
   where reading the source "confirmed" a mechanism that only a probe actually established.

**One recorded figure moved, and nothing painted differently.** The 320 px no-image total went
**0.19547 to 0.19716**, because the transparent shadow is now in the painted rect from first paint. No pixel
changed — a transparent shadow cannot paint — and criterion 22 asserts the *equality* of the two totals, not
either absolute value, so the assertion is unaffected. But any figure recorded as "0.19547 at 320 px with no
image" is now stale, and the "no-image default is unchanged from HEAD" invariant that 012 and the halo both
lean on is true **in pixels and false in this metric**. Stated here so the next reader does not treat the
move as a regression.

### 2026-11-06 — A `liveQuery` that races any repository call silently subscribes to nothing
Found while verifying task 014's frontend pass, fixed in `lib/db/database.ts`. **Pre-existing, and it
predates 014** — on HEAD it showed as pinning a task leaving `CurrentTaskCard` on its old copy.

**Symptom.** On `/` with a background image stored, adding or ticking a task did not update the card or the
task panel until a reload. With no image stored, everything updated live. A subscription mounted *later* —
the dialog's own list — worked fine, which is the clue that this was about mount timing, not the querier.

**The symptom's description was wrong, and that matters more than the fix.** It is not about background
images and not about any particular table. Measured, control 1 re-fire against 0:
a background row merely existing is harmless; a concurrent `loadBackground` breaks it; **a concurrent
`listTasks()` — the same table the query reads — breaks it identically.** The background image is only the
thing that reliably causes a concurrent repository call at mount on `/`. So the task list could go stale in
other situations too, and anything that adds a read at mount can resurrect this.

**Mechanism, confirmed with a probe reading `Dexie.Promise.PSD.subscr` either side of the await.** Inside a
liveQuery querier, Dexie makes the global `Promise` its own zone-aware one, so a promise *constructed there*
carries the zone. `openDatabase()` shared one attempt across callers (`if (pendingOpen) return pendingOpen`).
Dexie defers a querier's first run, so a concurrent repository call gets there first, **outside** any Dexie
zone, where `Promise` is native — and it is that native promise the querier then awaits. The zone does not
survive the await, Dexie's echo does not cover it, the reads afterwards are attributed to no subscription,
and the observability set comes out empty. The query then never re-fires. **Which zone resolved the promise
is not the cause**; the cause is a shared *native* promise created outside the awaiter's zone.

**Two hypotheses were disproved on the way, recorded so nobody pays for them twice.**
1. *"Awaiting a native promise before the Dexie read loses the zone."* False as stated. A querier awaiting
   `Promise.resolve(db)`, a `setTimeout(0)` macrotask, and a `new Promise` wrapper around `db.open()` all
   re-fire normally. The native promise only matters when it was **created in another zone and shared**.
2. *"The orchestrator confirmed the mechanism by reading the source."* It had not. Reading `openDatabase()`
   confirmed only that every path returns a native promise, which turns out to be irrelevant on its own.
   The shape was visible in the source; the cause was not, and only a probe settled it.

**Fix.** The old body is a private `openShared()`, unchanged — it keeps the single `pendingOpen`, the
blocked timer, `DatabaseBlockedError`, `DatabaseUnavailableError` and retry-after-reject. `openDatabase()`
now hands every caller `new Promise((resolve, reject) => shared.then(resolve, reject))`, **constructed in
the caller's own zone**, so inside a liveQuery it is a zone-aware promise and the awaiter resumes in its own
zone. Every repository read already awaits `openDatabase()`, so one wrapper covers every current and future
repository, and no repository or hook has to know zones exist. Call-order sharing is preserved: each wrapper
subscribes to `shared` in call order and every caller takes the same extra hop.

**For whoever writes the permanent test:** `liveQuery` silently does nothing if no `PomotatoDatabase` has
ever been constructed, because Dexie checks `domDeps` at query time. Call `getDatabase()` first or the test
passes for the wrong reason. A red-proof is cheap here and was taken at unit level — no browser needed,
which is why this was worth chasing before shipping rather than after.
